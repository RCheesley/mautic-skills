# Campaigns — behaviour specification (Mautic 7.x)

Every item states an observable outcome and its source. Paths are relative to the Mautic repo root.
Terms: Contact = `Lead` in code; membership = `campaign_leads` row; rotation = the numbered pass of a Contact through a campaign;
log = `campaign_lead_event_log` row; "no"/inactive path = red path in the UI; "yes" path = green path.

## 1. Lifecycle overview
1. Build: the user draws sources and events; on save the canvas connections become `parent_id` + `decision_path` + `event_order` [code: app/bundles/CampaignBundle/Controller/CampaignController.php:914-961 @7.x] [code: app/bundles/CampaignBundle/Model/CampaignModel.php:220-431 @7.x].
2. Membership: `mautic:campaigns:update` adds Contacts from published source Segments and flags those who left; Forms, UI, API and the Change Campaigns action add members through `MembershipManager` [code: app/bundles/CampaignBundle/Membership/MembershipBuilder.php:37-190 @7.x] [code: app/bundles/CampaignBundle/Membership/MembershipManager.php:37-131 @7.x].
3. Kickoff: `mautic:campaigns:trigger` phase 1 runs or schedules root events for members with no log in the current rotation [code: app/bundles/CampaignBundle/Executioner/KickoffExecutioner.php:130-191 @7.x].
4. Execution: an executed action dispatches its `batchEventName`; passed Contacts flow to child conditions and actions [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:109-205,331-367 @7.x].
5. Scheduled phase (phase 2) runs due logs after re-validating their date [code: app/bundles/CampaignBundle/Executioner/ScheduledExecutioner.php:76-338 @7.x].
6. Decisions: yes path in real time; no path in phase 3 [code: app/bundles/CampaignBundle/Executioner/RealTimeExecutioner.php:58-112 @7.x] [code: app/bundles/CampaignBundle/Executioner/InactiveExecutioner.php:184-257 @7.x].
7. Exit/restart: removal unschedules pending logs; a permitted re-add starts a new rotation and kickoff runs again [code: app/bundles/CampaignBundle/Membership/Action/Remover.php:35-59 @7.x] [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:48-83 @7.x].
8. Observation: logs feed detail stats, the Contact timeline, reports and optionally `campaign_summary` [code: app/bundles/CampaignBundle/Entity/LeadEventLogRepository.php:226-334 @7.x].

## 2. Sources and membership
- B1. Sources are Segments (`campaign_leadlist_xref`) and Forms (`campaign_form_xref`); saving requires ≥1 event and ≥1 source, in UI and API [code: app/bundles/CampaignBundle/Controller/CampaignController.php:914-936 @7.x] [code: app/bundles/CampaignBundle/Controller/Api/CampaignApiController.php:184-193 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#getting-started-with-campaign-builder].
- B2. Only published Segments feed membership (`lead_lists.is_published = 1`) [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:509-531 @7.x]. The builder's Segment selector offers public Segments only [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#getting-started-with-campaign-builder].
- B3. `mautic:campaigns:update` first adds Contacts in any source Segment (`lead_lists_leads.manually_removed = 0`) with no `campaign_leads` row, then removes orphaned members; unpublished campaigns are skipped [code: app/bundles/CampaignBundle/Membership/MembershipBuilder.php:37-61 @7.x] [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:396-429 @7.x] [code: app/bundles/CampaignBundle/Command/UpdateLeadCampaignsCommand.php:206-208 @7.x].
- B4. Allow restart off: a Contact with any log in the campaign is excluded from (re)adding by the rebuild, even if the membership row was deleted [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:376-378,417-419,593-608 @7.x].
- B5. Allow restart on: the rebuild excludes active members and manually removed members (`manually_removed=1 AND date_last_exited IS NULL`); Contacts removed by exit (`date_last_exited` set) are candidates again [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:533-563 @7.x].
- B6. Removal sets `manually_removed=1`, `manually_added=0`, `date_last_exited` = now for an exit (rebuild or Change Campaigns action) or null for manual UI/API removal; scheduled logs of the current rotation are unscheduled with a failed-log reason "Contact removed from campaign on %date%" [code: app/bundles/CampaignBundle/Membership/Action/Remover.php:35-59 @7.x] [code: app/bundles/CampaignBundle/Entity/LeadEventLogRepository.php:594-637 @7.x].
- B7. Removing an already removed Contact throws `ContactAlreadyRemovedFromCampaignException`, which `MembershipManager` swallows [code: app/bundles/CampaignBundle/Membership/Action/Remover.php:44-49 @7.x] [code: app/bundles/CampaignBundle/Membership/MembershipManager.php:165-172,201-209 @7.x].
- B8. Orphan removal touches only `manually_added = 0` members [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:434-483 @7.x].
- B9. A new membership starts at rotation 1, or 2 if the Contact already has rotation-1 logs (pre-2.14 BC); `manually_added` records whether the add was manual [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:22-41 @7.x].
- B10. Restart disabled: the only permitted re-entry is a manual re-add of a manually removed Contact; anything else throws `ContactCannotBeAddedToCampaignException('Contacts cannot restart the campaign')` [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:48-64 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/creating_campaigns.html#create-your-first-campaign].
- B11. Restart enabled: a manually removed Contact is still not re-added by an automatic action ('Contact was manually removed') [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:66-70 @7.x].
- B12. A re-add clears `manually_removed`, nulls `date_last_exited`, increments `rotation`, resets `date_added`; older-rotation logs stay; the Contact restarts from root events [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:72-82 @7.x] [code: app/bundles/CampaignBundle/Entity/Lead.php:213-219 @7.x].
- B13. Membership changes dispatch `CAMPAIGN_ON_LEADCHANGE` (single) or `LEAD_CAMPAIGN_BATCH_CHANGE` (batch) with action `added`/`removed`; LeadBundle writes timeline entries from them [code: app/bundles/CampaignBundle/Membership/MembershipManager.php:56,84,131,164,214 @7.x] [code: app/bundles/LeadBundle/EventListener/TimelineEventLogCampaignSubscriber.php:33-34 @7.x].
- B14. A Form submission adds the Contact (manual) to every published campaign using the Form as source; UI, batch and API add/remove also use `MembershipManager` [code: app/bundles/FormBundle/Model/SubmissionModel.php:382-387 @7.x] [code: app/bundles/LeadBundle/Controller/LeadController.php:1680-1686 @7.x] [code: app/bundles/CampaignBundle/Controller/Api/CampaignApiController.php:136,163 @7.x].
- B15. `--max-contacts` caps one campaign's rebuild (adds and removes both count) [code: app/bundles/CampaignBundle/Membership/MembershipBuilder.php:117-121,177-181 @7.x].
- B16. Membership queries use the read replica when configured, except when targeting specific Contact ids [code: app/bundles/CampaignBundle/Entity/ReplicaConnectionTrait.php:20-34 @7.x].

## 4. Kickoff
- B21. Kickoff Contacts: `manually_removed = 0` and no log for the current rotation [code: app/bundles/CampaignBundle/Entity/CampaignRepository.php:398-452 @7.x].
- B22. Root events = non-deleted parentless events; a campaign with none is skipped [code: app/bundles/CampaignBundle/Entity/Campaign.php:411-422 @7.x] [code: app/bundles/CampaignBundle/Executioner/KickoffExecutioner.php:93-97 @7.x].
- B23. Per root event and batch, one shared "now" is used; the event is scheduled for every Contact if its date is in the future or Contact-specific timing applies, else executed [code: app/bundles/CampaignBundle/Executioner/KickoffExecutioner.php:130-191 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:315-346 @7.x].
- B24. Every executed or scheduled event writes exactly one log per Contact per rotation (unique `campaign_rotation`) [code: app/bundles/CampaignBundle/Entity/LeadEventLog.php:125 @7.x] [code: app/bundles/CampaignBundle/Executioner/Logger/EventLogger.php:171-195 @7.x].

## 5. Scheduling, trigger modes and timezones
- B25. `immediate`, `optimized` and null (decisions) execute now; `interval` = later of (reference + interval, now); `date` = trigger date, or now if past [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:142-172 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/Interval.php:30-63 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/DateTime.php:15-35 @7.x].
- B26. Schedule decision compares at minute precision (`Y-m-d H:i`) unless env `CAMPAIGN_EXECUTIONER_SCHEDULER_ACKNOWLEDGE_SECONDS` is truthy [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:289-300 @7.x].
- B27. Contact-specific dates are required for `optimized`, and for `interval` with unit i/h/d/m/y plus any of trigger hour, start+stop hours, or days of week, unless the event is a no-path action under a decision; such events are always scheduled and grouped by computed date [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/Interval.php:138-177 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:302-337 @7.x].
- B28. Hour/day rules use `leads.timezone` if valid, else the system timezone. Trigger hour: that hour today if not passed, else the interval date itself. Start/stop window (swapped if reversed): before → start today; inside → now; after → start tomorrow. Days of week 0=Sunday…6 advance day by day; if the day changed and an hour is set the time resets to it; 7 throws `LogicException` [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/Interval.php:220-360 @7.x].
- B29. `optimized` is offered only for `email.send`, `message.send`, `plugin.leadpush`, `campaign.sendwebhook`; dates come from `PeakInteractionTimer::getOptimalTime()` or `getOptimalTimeAndDay()` when `triggerWindow = 1` [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/Optimized.php:20-39 @7.x] [code: app/bundles/CampaignBundle/Form/Type/EventType.php:60-62 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#smart-event-schedule].
- B30. On no-path actions under a decision the form hides `immediate` and relabels interval/date as inaction delays; default mode `interval`, unit `d`, interval 1 [code: app/bundles/CampaignBundle/Form/Type/EventType.php:64-76,113-127 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#notes-on-campaign-actions].
- B31. When a scheduled log is due the date is recomputed from the log's `date_triggered` (creation) + interval; if still future, it is rescheduled with note "Bulk rescheduling of events" [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:233-255 @7.x] [code: app/bundles/CampaignBundle/Executioner/ScheduledExecutioner.php:279-338 @7.x].
- B32. Due logs: `is_scheduled=1 AND trigger_date <= now (UTC) AND version = 1 AND campaign.is_published = 1`; `executeByIds` (`mautic:campaigns:execute`) requires the campaign not deleted and ignores `version` [code: app/bundles/CampaignBundle/Entity/LeadEventLogRepository.php:416-482 @7.x].
- B33. Jump-to-event logs run after all other logs in `executeByIds`; in normal execution jump events run after siblings [code: app/bundles/CampaignBundle/Executioner/ScheduledExecutioner.php:452-480 @7.x] [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:171-205 @7.x].

## 6. Publish state and republish behaviour
- B34. A campaign is unpublished if `is_published=0`, publish-up is future, or publish-down passed; update, trigger, resume-stuck skip it; real-time decisions require published, in dates, not deleted [code: app/bundles/CoreBundle/Entity/FormEntity.php:233-251,412-434 @7.x] [code: app/bundles/CampaignBundle/Entity/EventRepository.php:85-96 @7.x]. Docs: deactivating stops processing immediately; scheduled events stay queued [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#activate-and-deactivate-campaigns].
- B35. Publishing without publish-up sets it to now (minute precision); every (re)publish resets events' `failed_count` [code: app/bundles/CampaignBundle/EventListener/CampaignEventSubscriber.php:62-87 @7.x].
- B36. Republish behaviour applies only to `interval` events with a non-empty interval. `count_all_time` (default): unchanged. `restart_on_publish`: last publish date + interval. `count_only_while_published`: last publish date + max(0, interval − seconds already published), using the audit log of publish changes. Per-campaign value overrides the global `campaign_republish_behavior`; null = global [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:177-226 @7.x] [code: app/bundles/CampaignBundle/Service/PublishStateService.php:28-303 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#campaign-reactivation-behavior].
- B37. Recomputed dates in the past execute immediately; future ones are rescheduled — lazily, when cron next evaluates the log, not at reactivation [code: app/bundles/CampaignBundle/Executioner/ScheduledExecutioner.php:287-299 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#activate-and-deactivate-campaigns].
- B38. Failure-driven unpublish uses `transactionalCampaignUnPublish()` (`SELECT … FOR UPDATE`; throws if already unpublished or version differs). Toggle confirmations embed the effective republish label [code: app/bundles/CampaignBundle/Model/CampaignModel.php:917-936 @7.x] [code: app/bundles/CampaignBundle/EventListener/PublishToggleSubscriber.php:29-56 @7.x].

## 7. Execution, failures and locking
- B39. Actions → `ActionExecutioner`, persist logs, then child conditions/actions for passed Contacts; conditions → yes children for passed, no children for failed; decisions → yes children for applicable [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:109-161,331-425 @7.x].
- B40. Each action/condition log must win an optimistic lock (`version` 1→2) or is skipped ("was skipped as it had been executed already"); if dispatch throws, unexecuted logs reset to version 1 [code: app/bundles/CampaignBundle/Executioner/Event/ActionExecutioner.php:52-77 @7.x] [code: app/bundles/CampaignBundle/Executioner/Event/ConditionExecutioner.php:39-51 @7.x] [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:131-142 @7.x].
- B41. Action listener gets `PendingEvent`; unprocessed log → `LogNotProcessedException`; passed and failed → `LogPassedAndFailedException` [code: app/bundles/CampaignBundle/Executioner/Dispatcher/ActionDispatcher.php:35-67,113-124 @7.x].
- B42. `pass()` clears error metadata, deletes failed-log row, sets `is_scheduled=0`, `date_triggered=now`; `passWithError()` passes but keeps `metadata.failed=1, reason` (not retried); `fail()` writes the failed-log row and optional reschedule interval [code: app/bundles/CampaignBundle/Event/PendingEvent.php:54-79,131-156,240-252 @7.x] [devdocs: https://devdocs.mautic.org/en/7.2/plugin_extensions/campaigns.html#executing-a-campaign-action].
- B43. Failed logs reschedule to now + listener interval, else now + `campaign_time_wait_on_event_false` (default `PT1H`, "never" possible); version reset to 1; failed-log rows of later-successful logs are deleted after `ON_EVENT_EXECUTED_BATCH` [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:117-137,412-433 @7.x] [code: app/bundles/CampaignBundle/EventListener/CampaignEventLogCleanupSubscriber.php:30-41 @7.x].
- B44. 100 failures of one Contact on one event → `failed_count++` and failure notification (owner → creator → admin); ≥100 members and `failed_count/members ≥ 35 %` → transactional unpublish and email to owner/author or `campaign_notification_email_addresses` [code: app/bundles/CampaignBundle/EventListener/CampaignEventSubscriber.php:28-32,98-141 @7.x] [code: app/bundles/CampaignBundle/Executioner/Helper/NotificationHelper.php:26-138 @7.x].
- B45. Legacy `eventName`/`callback` actions run one log at a time with `E_USER_DEPRECATED`; `false` fails, `['failed'=>1,'reason'=>…]` passes with error [code: app/bundles/CampaignBundle/Executioner/Dispatcher/LegacyEventDispatcher.php:37-109,150-216 @7.x].
- B46. `lead.deletecontact` deletes Contacts and their logs are dropped, not persisted [code: app/bundles/LeadBundle/EventListener/CampaignActionDeleteContactSubscriber.php:50-62 @7.x] [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:289-323 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#notes-on-campaign-actions].
- B47. `campaign.addremovelead` adds (manual) / removes (exit) the batch; `this` targets the running campaign and, with restart allowed, re-enters the Contact in a new rotation [code: app/bundles/CampaignBundle/EventListener/CampaignActionChangeMembershipSubscriber.php:54-135 @7.x]. Docs: "You must remove a Contact from a Campaign before restarting the Campaign" [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#actions].
- B48. Adding to `this` is rejected when the event is `immediate` or an interval under 30 minutes; enforced in form and entity validation [code: app/bundles/CampaignBundle/Form/Validator/Constraints/InfiniteLoopValidator.php:28-45 @7.x] [code: app/bundles/CampaignBundle/EventListener/CampaignActionChangeMembershipSubscriber.php:89-108 @7.x].

## 8. Jump to Event
- B49. `campaign.jump_to_event` has no outgoing connections; on execution it increments `campaign_leads.rotation`, then schedules or runs the target relative to the jump's trigger date or now; a missing target passes with error "target does not exist" [code: app/bundles/CampaignBundle/EventListener/CampaignActionJumpToEventSubscriber.php:46-106 @7.x].
- B50. Loop protection is the rotation increment; there is no explicit iteration cap. `JumpToActionTest::testInfiniteLoop` asserts a decision → jump → loop leaves exactly 3 logs after two trigger runs ("This was 6 before the fix") [code: app/bundles/CampaignBundle/Tests/Functional/Campaign/JumpToActionTest.php:20-180 @7.x].

Temp jump target ids (`new…`) resolve to real ids in `CAMPAIGN_POST_SAVE` (priority 1); cloning rewrites `jumpToEvent` [code: app/bundles/CampaignBundle/EventListener/CampaignActionJumpToEventSubscriber.php:115-143 @7.x] [code: app/bundles/CampaignBundle/Controller/CampaignController.php:764-770 @7.x].

- B54. ## 10. Inactive ("no") path
- B56. Only decisions with no-path children (or deleted with redirect) are considered; Contacts with no log for the decision this rotation; with a parent, the parent log must exist; for a root decision the Contact must have no log at all this rotation [code: app/bundles/CampaignBundle/Executioner/InactiveExecutioner.php:143-152 @7.x] [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:168-252 @7.x].
- B57. Inactive when the earliest no-child date, computed from the parent's `date_triggered` (or `campaign_leads.date_added` for root decisions), ≤ now; scheduled parent logs skip. Decision log gets `non_action_path_taken=1`; the earliest child runs now, later ones keep relative dates [code: app/bundles/CampaignBundle/Executioner/Helper/InactiveHelper.php:48-146 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:262-287 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#red-paths].
- B58. Inactive-path logs and false conditions set `non_action_path_taken=1`; detail-page yes/no percentages and timeline icons derive from it [code: app/bundles/CampaignBundle/Executioner/Logger/EventLogger.php:83-85 @7.x] [code: app/bundles/CampaignBundle/Executioner/Event/ConditionExecutioner.php:57-60 @7.x].

## 11. Conditions
- B59. Condition listeners receive `ConditionEvent` on their `eventName` and on `ON_EVENT_CONDITION_EVALUATION`; `fail()` or `ConditionFailedException` → no path; every condition log gets `date_triggered=now` [code: app/bundles/CampaignBundle/Executioner/Dispatcher/ConditionDispatcher.php:18-25 @7.x] [code: app/bundles/CampaignBundle/Executioner/Event/ConditionExecutioner.php:33-84 @7.x]. ## 12. Log states and manual rescheduling
- B60. Scheduled: `is_scheduled=1, trigger_date>now`; executed: `is_scheduled=0, date_triggered` set; cancelled: `is_scheduled=0 AND date_triggered IS NULL`; failed: failed-log row / `metadata.failed`; `date_queued` for external queues, cleared on reschedule [code: app/bundles/CampaignBundle/Entity/LeadEventLogRepository.php:110-128,683-697 @7.x] [code: app/bundles/CampaignBundle/EventListener/LeadSubscriber.php:105-114 @7.x].
- B61. API/AJAX date changes go through `rescheduleLogs()` and fire `ON_EVENT_SCHEDULED_BATCH` with `isReschedule=true`; decisions cannot be scheduled; executed events cannot be edited; non-members error; AJAX dates must be ≥ now; cancel sets `is_scheduled=0` and `metadata.errors` [code: app/bundles/CampaignBundle/Model/EventLogModel.php:82-213 @7.x] [code: app/bundles/CampaignBundle/Controller/AjaxController.php:55-108 @7.x]. Docs: trigger-date changes are visible in the timeline under "Campaign Event Scheduled" [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#tracking-rescheduled-events].
