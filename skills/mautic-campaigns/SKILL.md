# Mautic Campaigns

## Scope
A Campaign is a workflow drawn on a canvas: Contacts enter from sources (Segments, Forms, manual or API adds) and flow through Actions (Mautic does something), Decisions (the Contact does something, or does not within a wait) and Conditions (Mautic checks Contact data). This skill covers the CampaignBundle: builder, membership, the execution engine, the event log, commands, API, import/export, and the plugin contract for new event types. What each channel action does once dispatched (sending an Email, an SMS, a webhook) belongs to the owning skill (mautic-emails, mautic-channels, …); cron scheduling and locking in general belong to mautic-cron-and-queues.

Terms used below: a **Contact** is a person record (code: `Lead`); a **Segment** is a filtered or static list of Contacts (code: `LeadList`); **membership** is the `campaign_leads` row for one Contact in one Campaign; a **rotation** is a numbered pass of one Contact through one Campaign; the **event log** is `campaign_lead_event_log` (one row per event per Contact per rotation); the **inactive path** ("no" path, red path in the UI) is what happens when a Contact does not perform a Decision's action in time.

## Expected behaviour (essentials)
- A campaign cannot be saved without at least one event and at least one source (Segment or Form), in the UI or in the API [code: app/bundles/CampaignBundle/Controller/CampaignController.php:914-936 @7.x] [code: app/bundles/CampaignBundle/Controller/Api/CampaignApiController.php:184-193 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/creating_campaigns.html#create-your-first-campaign].
- Nothing happens without cron: `mautic:campaigns:update` (alias of `mautic:campaigns:rebuild`) syncs Segment members into the campaign, and `mautic:campaigns:trigger` runs kickoff, then scheduled, then inactive phases for each published campaign [code: app/bundles/CampaignBundle/Command/UpdateLeadCampaignsCommand.php:162-234 @7.x] [code: app/bundles/CampaignBundle/Command/TriggerCampaignCommand.php:243-271 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#triggering-campaign-events].
- Only published Segments feed membership; unpublished campaigns (including "pending" with a future publish-up and "expired" with a past publish-down) are skipped by update, trigger and resume-stuck [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:509-531 @7.x] [code: app/bundles/CoreBundle/Entity/FormEntity.php:233-251 @7.x] [code: app/bundles/CampaignBundle/Command/TriggerCampaignCommand.php:306-308 @7.x].
- Form sources add the submitter immediately on submission (manual add) to every published campaign that uses the Form; no cron is needed for that step [code: app/bundles/FormBundle/Model/SubmissionModel.php:382-387 @7.x].
- Removing a member never deletes the `campaign_leads` row: it sets `manually_removed=1`, sets `date_last_exited` to now for an "exit" (Segment rebuild or the Change Campaigns action) or null for a manual UI/API removal, and cancels the Contact's scheduled events for the current rotation [code: app/bundles/CampaignBundle/Membership/Action/Remover.php:35-59 @7.x].
- The Segment rebuild only removes members with `manually_added=0`; Contacts added by hand, API, Form submission or campaign action stay even when they leave the source Segment [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:434-483 @7.x].
- With "Allow restart" off, a Contact who ever has an event log in the campaign is never re-added by the rebuild; the only re-entry allowed is a manual re-add of a manually removed Contact [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:376-378 @7.x] [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:48-64 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/creating_campaigns.html#create-your-first-campaign].
- With "Allow restart" on, an exited Contact who re-qualifies is re-added in a new rotation and restarts from the root events; a manually removed Contact is still never re-added automatically [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:66-82 @7.x] [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:533-563 @7.x].
- One log per event per Contact per rotation is enforced by the unique key `campaign_rotation(event_id, lead_id, rotation)`, so an event cannot run twice for a Contact in the same rotation [code: app/bundles/CampaignBundle/Entity/LeadEventLog.php:125 @7.x].
- Kickoff picks members (`manually_removed=0`) that have no log at all for their current rotation and runs or schedules every root event for them [code: app/bundles/CampaignBundle/Entity/CampaignRepository.php:398-452 @7.x] [code: app/bundles/CampaignBundle/Executioner/KickoffExecutioner.php:130-191 @7.x].
- Decisions' positive ("yes"/green) path never runs from cron; it runs in real time when the owning bundle calls `RealTimeExecutioner::execute()` for the tracked, identified Contact [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:258-263 @7.x] [code: app/bundles/CampaignBundle/Executioner/RealTimeExecutioner.php:58-112,168-176 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#green-paths].
- The inactive path is evaluated by the trigger command's third phase: once the earliest delay on the decision's "no" children has elapsed since the parent event fired (or since the Contact joined, for a root decision), the decision is logged with `non_action_path_taken=1` and the "no" children run [code: app/bundles/CampaignBundle/Executioner/Helper/InactiveHelper.php:48-146 @7.x] [code: app/bundles/CampaignBundle/Executioner/InactiveExecutioner.php:225-231,265-309 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#red-paths].
- A Decision fires once per rotation: after "Visits a page" fired, later visits do not re-trigger it [docs: https://docs.mautic.org/en/7.2/campaigns/troubleshooting_campaigns.html#page-visits-aren-t-recognized] [code: app/bundles/CampaignBundle/Entity/EventRepository.php:56-111 @7.x].
- Conditions are evaluated immediately when reached; a Contact does not wait for a condition to become true [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#using-a-custom-date-field-to-trigger-a-campaign] [code: app/bundles/CampaignBundle/Executioner/Event/ConditionExecutioner.php:33-84 @7.x].
- Trigger modes: `immediate` runs now; `interval` adds N i/h/d/m/y to the reference date; `date` uses the fixed date or now if past; `optimized` picks a per-Contact best time and is offered only for `email.send`, `message.send`, `plugin.leadpush` and `campaign.sendwebhook` [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:142-172 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/Optimized.php:20 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#smart-event-schedule].
- Hour and weekday restrictions on an interval event are computed in the Contact's timezone (`leads.timezone`), falling back to the system timezone; such events are always scheduled, never run inline [code: app/bundles/CampaignBundle/Executioner/Scheduler/Mode/Interval.php:138-177,322-360 @7.x].
- Scheduling compares at minute precision: an event due within the current minute runs now, unless `CAMPAIGN_EXECUTIONER_SCHEDULER_ACKNOWLEDGE_SECONDS` is set [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:289-300 @7.x].
- When a scheduled log comes due, its date is recomputed from creation time plus interval with the hour/day rules and republish behaviour; if that date is still in the future the log is rescheduled, not executed [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:233-255 @7.x] [code: app/bundles/CampaignBundle/Executioner/ScheduledExecutioner.php:279-338 @7.x].
- Republish behaviour (UI: "Campaign Republish Behaviour" / docs: "Reactivation behaviour") affects only interval events: `count_all_time` (default) keeps original dates; `restart_on_publish` restarts the delay from the last publish date; `count_only_while_published` excludes unpublished time [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:177-226 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#campaign-reactivation-behavior].
- Publishing a campaign with no publish-up date sets publish-up to now; every (re)publish resets all events' `failed_count` to 0 [code: app/bundles/CampaignBundle/EventListener/CampaignEventSubscriber.php:62-87 @7.x].
- An action listener must pass or fail every log in the batch; a failed log is retried after the listener's interval, else `campaign_time_wait_on_event_false` (default `PT1H`), and is not retried if neither is set [code: app/bundles/CampaignBundle/Executioner/Dispatcher/ActionDispatcher.php:35-107 @7.x] [code: app/bundles/CampaignBundle/Executioner/Scheduler/EventScheduler.php:117-137,412-433 @7.x] [devdocs: https://devdocs.mautic.org/en/7.2/plugin_extensions/campaigns.html#executing-a-campaign-action].
- A Contact failing the same event 100 times bumps the event's `failed_count` and notifies; a campaign with at least 100 members whose `failed_count` reaches 35 % of members is unpublished automatically and the owner is emailed [code: app/bundles/CampaignBundle/EventListener/CampaignEventSubscriber.php:28-32,98-141 @7.x].
- Two workers cannot execute the same action or condition log: each log is claimed by an optimistic `version` bump, and scheduled logs are only fetched while `version = 1` [code: app/bundles/CampaignBundle/Executioner/Event/ActionExecutioner.php:52-77 @7.x] [code: app/bundles/CampaignBundle/Entity/LeadEventLogRepository.php:416-457 @7.x].
- Jump to Event is terminal (no outgoing connections); it increments the Contact's rotation, then schedules or runs the target event [code: app/bundles/CampaignBundle/EventListener/CampaignActionJumpToEventSubscriber.php:46-106 @7.x].
- Deleting an event in the builder soft-deletes it; Contacts scheduled on it can be redirected to another event, which happens at execution time and starts a new rotation for those Contacts [code: app/bundles/CampaignBundle/Executioner/Helper/EventRedirectionHelper.php:35-121 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#identifying-campaign-events].
- Deleting a campaign removes its event logs (unless background deletion is configured) and the campaign row; Contacts' own activity (Emails sent, page hits) stays [code: app/bundles/CampaignBundle/EventListener/CampaignEventDeleteSubscriber.php:34-45 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#deleting-a-campaign].
- Import always creates or updates campaigns as unpublished; matching is by `uuid` [code: app/bundles/CampaignBundle/EventListener/CampaignImportExportSubscriber.php @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/importing_campaigns.html#activating-an-imported-campaign].
- `PUT /api/campaigns/{id}/edit` deletes every event and source missing from the payload, and each event in a PUT must carry an `id` [code: app/bundles/CampaignBundle/Controller/Api/CampaignApiController.php:179-218 @7.x].
- A stored event whose type is no longer registered (plugin disabled or removed) cannot be executed: `EventCollector` throws `TypeNotFoundException` / `EventNotFoundException` [code: app/bundles/CampaignBundle/EventCollector/EventCollector.php:26-84 @7.x].

## How to change or extend it
- Add a new campaign event type from your own bundle: subscribe to `CampaignEvents::CAMPAIGN_ON_BUILD` (7.x) and call `addAction()`, `addDecision()` or `addCondition()` on `CampaignBuilderEvent` [code: app/bundles/CampaignBundle/Event/CampaignBuilderEvent.php:50-196 @7.x] [devdocs: https://devdocs.mautic.org/en/7.2/plugin_extensions/campaigns.html#registering-campaign-events]. To support 7.x and 8.x, subscribe on `CampaignBuilderEvent::class` and add the constant key only when `defined()` [devdocs: https://devdocs.mautic.org/en/8.0/plugin_extensions/campaigns.html#registering-campaign-events].
- Actions: register `batchEventName`, never `eventName`/`callback`; listen for `PendingEvent` and call `pass()`, `passWithError()` or `fail()` on every log (leaving one unprocessed throws `LogNotProcessedException`) [code: app/bundles/CampaignBundle/Executioner/Dispatcher/ActionDispatcher.php:35-67,113-124 @7.x]. Legacy actions are deprecated in 7.x and are not executed at all in 8.x [code: app/bundles/CampaignBundle/Executioner/Dispatcher/LegacyEventDispatcher.php:152,181 @7.x] [PR #17097].
- Conditions: register `eventName`; the listener gets `ConditionEvent` and must call `pass()` or `fail()` [code: app/bundles/CampaignBundle/Executioner/Dispatcher/ConditionDispatcher.php:18-25 @7.x].
- Decisions: register `eventName`; from your bundle's activity handler call `RealTimeExecutioner::execute($type, $passthrough, $channel, $channelId)`; your listener gets `DecisionEvent` and calls `setAsApplicable()` [code: app/bundles/CampaignBundle/Executioner/RealTimeExecutioner.php:58-112 @7.x] [devdocs: https://devdocs.mautic.org/en/7.2/plugin_extensions/campaigns.html#evaluating-a-campaign-decision].
- Restrict canvas connections with `connectionRestrictions` (`source`, `target`, `anchor`); `associatedActions`/`associatedDecisions`/`anchorRestrictions` are deprecated and ignored in 8.x [code: app/bundles/CampaignBundle/EventCollector/Builder/ConnectionBuilder.php:16-107 @7.x] [PR #17032].
- Set `channel` and `channelIdField` on the registration so logs carry the channel; `channel_id` is stored only when one numeric id is selected [code: app/bundles/CampaignBundle/Helper/ChannelExtractor.php:11-59 @7.x].
- Never rename an event key (`type`) of a shipped event: stored `campaign_events.type` values reference it, and unknown types cannot run [code: app/bundles/CampaignBundle/EventCollector/EventCollector.php:26-84 @7.x].
- A schema change to any campaign table needs a Doctrine migration plus the entity metadata, the API serializer groups (`campaign`, `campaignBasic`, `campaignEventWithLogsDetails`) and the import/export subscribers, which serialise campaigns and events field by field [code: app/bundles/CampaignBundle/Entity/Campaign.php:228-267 @7.x] [code: app/bundles/CampaignBundle/EventListener/CampaignEventImportExportSubscriber.php @7.x].
- Membership changes must go through `MembershipManager` so the rules, unscheduling and `CAMPAIGN_ON_LEADCHANGE` / `LEAD_CAMPAIGN_BATCH_CHANGE` events stay consistent [code: app/bundles/CampaignBundle/Membership/MembershipManager.php:37-219 @7.x].
- Changing a log's trigger date must go through `EventScheduler::rescheduleLogs()` so `metadata.triggerDateLog` and `ON_EVENT_SCHEDULED_BATCH` stay correct [code: app/bundles/CampaignBundle/Model/EventLogModel.php:204-213 @7.x].

## Version notes
- Campaign import/export exists only from 7.0 [docs: https://docs.mautic.org/en/7.2/campaigns/exporting_campaigns.html]. Event copy/paste in the builder exists from 5.1 [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#cloning-campaign-events].
- 7.2 deprecates the `mautic.campaign.event_collector` service alias [code: app/bundles/CampaignBundle/Config/services.php:69-70 @7.x]; `campaigns_resume_stuck_records_after` defaults to `2025-10-01 00:00:00` [code: app/bundles/CampaignBundle/Config/config.php:174 @7.x].
- 8.x removes 21 `CampaignEvents` constants (only `ON_EVENT_DECISION_EVALUATION`, `ON_EVENT_CONDITION_EVALUATION`, `ON_EVENT_JUMP_TO_EVENT`, `ON_CAMPAIGN_ACTION_CHANGE_MEMBERSHIP` remain); subscribe by event class (`CampaignBuilderEvent::class`, `CampaignSingleLeadChangeEvent::class`, `CampaignPostSaveEvent::class`, …) [PR #17161] [PR #17225] [devdocs: https://devdocs.mautic.org/en/8.0/plugin_extensions/campaigns.html#campaign-membership-change-events].
- 8.x deletes `LegacyEventDispatcher`: `eventName`/`callback` actions and every `*Events::ON_CAMPAIGN_TRIGGER_ACTION` constant are gone; core actions use `ON_CAMPAIGN_BATCH_ACTION` [PR #17097].
- 8.x makes `CampaignLeadChangeEvent` abstract and removes `ConditionEvent`/`DecisionEvent::getResult()/setResult()` [PR #17151]; adds `wasConditionSatisfied()` / `wasDecisionApplicable()` to the documented API [devdocs: https://devdocs.mautic.org/en/8.0/plugin_extensions/campaigns.html#evaluating-a-campaign-condition].
- Full list: `references/version-notes.md`.

## Pitfalls
- A locked trigger/update command prints "Script in progress" and exits 0, so a stuck lock looks like a successful run [code: app/bundles/CoreBundle/Command/ModeratedCommand.php:113-117 @7.x].
- `ON_EVENT_CONDITION_EVALUATION` and `ON_EVENT_DECISION_EVALUATION` share one string; a listener on either receives both `DecisionEvent` and `ConditionEvent` [code: app/bundles/CampaignBundle/CampaignEvents.php:171,189 @7.x].
- Testing a page-visit decision while logged in to Mautic does not trigger it; use a private browser session [docs: https://docs.mautic.org/en/7.2/campaigns/troubleshooting_campaigns.html#page-visits-aren-t-recognized]. Anonymous (unidentified) Contacts never fire decisions [code: app/bundles/CampaignBundle/Executioner/RealTimeExecutioner.php:168-176 @7.x].
- The "Allow restart" tooltip says a Contact "removed for any reason then added back" restarts, but code still blocks automatic re-add of a manually removed Contact [code: app/bundles/CampaignBundle/Translations/en_US/messages.ini:3 @7.x] [code: app/bundles/CampaignBundle/Membership/Action/Adder.php:66-70 @7.x].
- A root decision is evaluated for the inactive path only for Contacts with no log at all in the rotation; a campaign with a root action next to a root decision never sends those Contacts down the decision's "no" path [code: app/bundles/CampaignBundle/Entity/LeadRepository.php:220-234 @7.x] (inferred from the query; not covered by docs).
- Events added later to a running campaign are not run retroactively by `mautic:campaigns:resume-stuck` for Contacts who already passed that point (`date_linked` rule) [code: app/bundles/CampaignBundle/Entity/CampaignRepository.php:742-743 @7.x].
- Delete Contact actions drop their own logs, so the campaign overview can show 0 % for that action [docs: https://docs.mautic.org/en/7.2/campaigns/campaign_builder.html#notes-on-campaign-actions] [code: app/bundles/CampaignBundle/Executioner/EventExecutioner.php:289-323 @7.x].
- "Change Campaigns" with `this` on an `immediate` or under-30-minute interval event is rejected as an infinite loop [code: app/bundles/CampaignBundle/Form/Validator/Constraints/InfiniteLoopValidator.php:28-45 @7.x].
- `--inactive-only` help text says "Just execute scheduled events"; it runs the inactive phase only [code: app/bundles/CampaignBundle/Command/TriggerCampaignCommand.php:137-142 @7.x].
- `mautic:campaigns:validate` without `--contact-id`/`--contact-ids` prints 0 and does nothing [code: app/bundles/CampaignBundle/Command/ValidateEventCommand.php:76-84 @7.x].
- Docs name the republish options "Restart on reactivation / Count delay only while active / Count delay regardless of activation state"; the UI labels are "Restart on republish / Count delay only while published / Count delay regardless of publish state" [code: app/bundles/CampaignBundle/Translations/en_US/messages.ini:194-199 @7.x] [docs: https://docs.mautic.org/en/7.2/campaigns/managing_campaigns.html#configuring-reactivation-behaviour].
- Dev docs show campaign export as `POST /api/campaigns/export/{id}`; the route is GET. Dev docs give import status "200 or 201"; the controller returns 201 [code: app/bundles/CampaignBundle/Config/config.php:131-140 @7.x] [code: app/bundles/CampaignBundle/Controller/Api/CampaignApiController.php:487 @7.x] [devdocs: https://devdocs.mautic.org/en/7.2/plugin_extensions/campaigns.html#exporting-via-api].
- `EventLogModel::updateContactEvent()` maps the `channelId` API field to `setChannel()`, which looks like a bug [code: app/bundles/CampaignBundle/Model/EventLogModel.php:193-195 @7.x].
- Open question: `campaign_by_range` is in the config form but no consumer was found in CampaignBundle [code: app/bundles/CampaignBundle/Form/Type/ConfigType.php:65-75 @7.x] [unverified].
